01 · The project

About Ami

Ami is a customer-support agent for Amazon. It handles order status, package tracking, cancellations, returns and refunds, and policy questions.

Without logging in, anyone can ask general questions (policies, shipping info, how-tos).

After logging in, a customer can access their own account — order lookups, tracking, cancellations and returns — and only their own: per-customer data isolation means one user can never see another's orders.

It looks up live order data with tools, quotes written policy from a knowledge base, and requires explicit confirmation before it changes anything.

When it can't help, it hands off to a human instead of guessing.

Objective

Harden Ami for production.
Take the existing agent and make it cheaper, observable, resilient, honest, and self-testing — proving every change with before/after numbers on a frozen test suite.

05 · What did NOT work mandatory

Six honest misses — reported, not hidden. Two are ours from review, which is the point of a readout:

MissWhy
Model routing cut no cost live The proxy ignores the requested model — every call returns gpt-5.6-terra. Logic is built & tested (−25% computed), but there's no cheaper tier to switch to here. Shipped off by default.
S1 target missed: −38% golden, −11% behavioural — not half Measured on PR #2: cost fell 38% (golden) and 11% (behavioural), short of "under half". Most of each call is a prompt prefix the proxy caches unpredictably — hit rate swung 79% → 48% between runs of the same suite — so dollars move less than tokens. Earlier, we disproved the "trimming forgets" fear (facts live in working memory, 3 tests), but the API token budget ran out (3M / 3M). The irony: the eval runs themselves — fat input tokens, the exact problem S1 targets — drained it. Added a token guard so the next key is protected.
Trimming can't be shown on the frozen suite Transcript trimming only cuts anything once a conversation is longer than the cap — and the longest frozen case is 14 messages. At the recommended cap (16) it fires on 0/20 cases; at an aggressive 8, on 5/20. So a same-suite before/after would read ~0 by construction, not because the lever is weak (17–25% on an 8-turn session). It is a long-chat lever and has to be reported outside the frozen suite. That is why the S1 fix we built instead is prefetch (#14), which acts on 13/20 frozen cases.
12-word cap on the ReAct thought — reverted (PR #2) Saved 13% of output cost and broke a guardrail: the behavioural suite fell 20/20 → 16/20 (a "store manager" override got a return started). Reverted, d07e8d3 → 81b0cf5.
The refusal-reason rule only half works (PR #2) Golden facts improved 0.84 → 0.98, but shipped / past-window refusals still drop the reason in about half the runs.
We saw the policy-path gap and explained it away On day one we found ReAct bypassing policy.guarded_run and called it "not a bug — the tool has its own check". It was the bug: a cancel could never complete, and our "flaky" confirmation cases were this. Shree's PR fixed it. Then our review of that PR caught a new scope leak it introduced — fixed before merge. Both are in the record because a readout that hides them is worth less.
